0. 一分钟看懂

豆包输入法打字时用的「语音输入」，本质是客户端把麦克风音频发到字节的流式识别服务。它不需要登录、也没有对外公开 API，但它的凭据是按设备匿名下发的，所以我们可以自己复刻整条链路：

你的程序 ──①注册匿名设备──▶ log.snssdk.com 得到 device_id ──②用 device_id 换 key─▶ is.snssdk.com/settings 得到 asr_config.app_key ──③连 WebSocket────────▶ frontier-audio-ime-ws.doubao.com │ StartTask → StartSession │ TaskRequest（16k PCM / 20ms 一帧） │ FinishSession ◀──── ④识别结果（累积文本 + 逐字时间）──────────────────┘
能不能直接用？能，实测在 Linux 服务器上跑通了中文、英文、中英混说。 但它是未公开的内部接口：凭据按设备下发、随时可能变更或加风控，请只用于技术研究与自用，别拿去做对外产品（想产品化用火山引擎官方接口或本地开源模型）。

1.3 识别协议

一条 WebSocket 长连接，二进制 protobuf 帧，四个步骤：

连接 wss://frontier-audio-ime-ws.doubao.com/ocean/api/v1/ws?aid=685343&device_id=<did> 头部 User-Agent: com.bytedance.android.doubaoime/... ← 伪装成官方客户端 proto-version: v2 ← 关键！没有它就回 JSON 而不是 protobuf x-custom-keepalive: true ① StartTask { token=app_key, service=ASR } → TaskStarted ② StartSession { payload=会话参数 JSON } → SessionStarted ③ TaskRequest ×N { audio=20ms PCM, frame_state=1/3/9 } → 结果 JSON（累积文本） ④ FinishSession → SessionFinished

请求字段（实测得到的字段号）

字段号类型含义值
2stringtoken第 ② 步拿到的 asr_config.app_key
3stringservice_nameASR
5stringmethod_nameStartTask / StartSession / TaskRequest / FinishSession
6stringpayloadJSON 字符串（会话参数 / 每帧的时间戳）
7bytesaudio_data16k/单声道/PCM16，20 ms = 640 字节
8stringrequest_id自己生成的 UUID，用于对账
9varintframe_state首帧 1、中间 3、末帧 9

StartSession 的 payload

{
  "audio_info": { "channel": 1, "format": "raw", "sample_rate": 16000 },
  "enable_punctuation": true,
  "enable_speech_rejection": false,
  "extra": {
    "did": "<device_id>",
    "input_mode": "tool",
    "strong_ddc": true,            // 强纠错
    "use_twopass_retry": true,     // 二遍重试
    "enable_asr_twopass": true,    // 流式 + 整段两遍解码
    "enable_asr_threepass": true,  // 三遍
    "disable_user_words": false,   // 允许个人词库生效
    "cell_compress_rate": 8,
    "context": "<base64>"          // 可选：chat + ime_info + hotwords（热词偏置）
  }
}
音频格式：format 除了 raw（16k PCM16，最省事）也支持 speech_opus（官方客户端用的 Opus）。 用 raw 就不必自己实现 Opus 编码，实测同样能识别。

响应字段

字段号含义
2task_id
4事件名：TaskStarted / SessionStarted / SessionFinished / TaskFailed / SessionFailed
5状态码（见下表）
6状态文本
7结果 JSON（识别文本、时间、是否定稿）

结果 JSON（字段 7 的内容）

{
  "results": [{
    "text": "你好，这是语音识别测试",      // 本次发言的累积文本，最后一条即完整结果
    "start_time": 1.33, "end_time": 3.4,  // 秒，相对本次会话起点
    "confidence": 0.998,
    "is_interim": false,                  // false = 已定稿
    "is_vad_finished": true,              // VAD 判定这一句说完了
    "index": 0,
    "alternatives": [{ "text": "…", "words": [
        { "word": "你", "start_time": 0, "end_time": 0.34 }, …   // 逐字时间
    ]}]
  }]
}
两个实测坑： ① 短语气词会被反复改字（唉→哎→唉），三条消息 start_time 完全相同、只有 end_time 在涨——判断"新的一段"必须看起点，不能只看文本； ② alternatives[].words[].end_time 偏大（带前瞻窗口），做字幕要用"下一句的首字时间 / 整段 end_time"校正。

原因是这个模型是 zh + en 双语（即官方宣传的"中英混输"），客户端创建识别句柄时写死的是 speech_opus + zh； 协议里没有 language 字段，所以没有"切语种"的开关。要用日语只能换官方多语种接口或在本地跑开源日语模型。

1.6 豆包的离线识别是怎么做的

这是本轮最有价值的发现。结论先给：离线识别 = 字节自研端侧推理引擎 Flute + 联网下载的模型包， 而且 Windows 0.9.2.7 里还没有这套东西（Android / macOS 有）。

层证据Windows 0.9.2.7macOS 1.0.2Android 1.5.1
端侧推理引擎 Flute flute/engine/engine.cc、flute_c_api.cc、flute/framework/*、 flute/base/filesystem_mmap/filesystem_packed_mmap.cc（打包 mmap 模型容器） 无主程序内libaudioeffect.so
ASR 模型结构 flute/module/asr/ntp_cif/{encoder_actor,cif_calculator,beam_searcher,decoder_context/prompt_processor}、 feature/{mel_bank,panther,subband}_feature_extractor、module/vad/v4、module/signal/aec 无有有
SAMI 的本地 worker speech_v2/asr/offline/{asr_off_singleton,asr_off_worker}.cpp、capi/flute/asr/flute_asr.cpp 有调度、无引擎有有
模型下载管理 应用侧 OimeOfflineModel 模块：ASROfflineModel{Manager,FileStore,PathResolver,MetaInfoService,Manifest}、 通知 start/pause/resume/retry/requestDelete/updateOfflineModelState、 日志 ASR offline model path:、缺模型弹窗 ASROfflineModelUnavailablePromptWindowController 无有（APK 内未打包模型）

模型长什么样

macOS 主程序里写死了模型的张量文件名（93 个 .bin/.dat/json），可以直接读出结构 —— 是 PANTHER Conformer 编码器 + LLM 风格解码器，CIF（连续积分激发）机制，int8 量化：

s/panther_conformer_*                     编码器
s/panther_decoder_L*                      解码器
s/panther_l0_{qkv_pre_rope,mha_raw,ffn1_gemm1,ffn2_swiglu,rmsnorm1,rmsnorm2,conv_out}.bin
up_proj.bin / down_proj.bin / v_proj.bin / swiglu.bin / o_proj ...   权重张量
*_shape.dat / input_shape.dat / config.json / token_config.json / llm_params.json

算力后端是 CPU int8（源码里有 PackBS8 format: 4x4 tiled layout matching CPU prepacked weights） 加 GPU kernel（macOS 用 Metal，源码里带 device const char* 的着色器）。体量对得上"离线模型包约 150 MB"的说法。

在线 / 离线怎么协同（SAMI 里的融合策略）

  • PutOnlineCacheAudioToOffline：把在线期间缓存的音频交给整段识别重跑
  • [online vs offline] words num: [%d vs %d]：两份结果对比择优
  • 触发条件：asr has no network, switch to offline、asr has no result, switch to offline、recv interval time
  • 时间参数：finish_wait_offline_time / offline_wait_online_time / max_wait_switch_offline_time
  • 应用侧：openASRPanel canceled: network disconnected, offlineModelStatus=、Skip smart text enable prompt: reason=offline_result
为什么不能直接拿客户端里的那份用： ① 模型是私有逐张量格式（SAMI 容器，载荷加密，熵 ≈ 8.0），引擎里写死了张量名； ② Flute 静态编进客户端（macOS 主程序 / Android 的 libaudioeffect.so），Windows 包里根本没有； ③ 客户端要的模型名是加密的（name_sec），扒不出它到底用哪个。
但这不等于拿不到可用的模型——字节的算法分发接口是公开的，里面有同架构的明文 ONNX，见 1.7。

1.7 离线模型能从公开渠道拿到（本项目已内置离线引擎）

本以为“只有私有引擎能吃这些模型”，结果发现字节把一批模型放在公开算法分发接口上，无需任何鉴权：

GET https://effect.snssdk.com/model/api/arithmetics?sdk_version=25.0.0
→ {"status_code":0,"data":{"arithmetics":{"cakeCook":[
     {"name":"lv_asr_support","version":"1.2",
      "file_url":{"url_list":["https://n98-lf-effect-aweme-302-ncdn.byteeffecttos.com/obj/ies.fe.effect/<md5>?module=model"],
                   "zip_url_list":["..."]}}]}}}

# 参数必须是小写 sdk_version（写 SdkVersion 会报 missing required parameter），只能 GET（POST 404）
# sdk_version 就是“面板版本”，值越大条目越多：1.0.2→3、15.0.0→875、25.0.0→1128（上限）

这条链路是怎么找到的（可复现）

  1. macOS 客户端主程序里有 ASROfflineModelMetaInfoService.swift、ASROfflineModelTTNetRequest （TTNet 是字节的网络库），顺着字符串邻域找到两个 TTNet 服务名 com.wave.offline-model.metainfo-service / com.wave.offline-model.metainfo-head；
  2. 同一片邻域里出现域名 https://effect.snssdk.com 与路径 /model/api/arithmetics （还有解析字段 fileDownloadURLs、installRelativePath、componentVersionKey）；
  3. 裸调该路径，服务端直接报 params check error: expr_path=SdkVersion, cause=missing required parameter—— 按提示试出参数名必须是小写 sdk_version（写成 SdkVersion 反而一直报缺参数），POST 一律 404（只收 GET）；
  4. 把 sdk_version 调大就能看出它是“面板版本”：1.0.2→3 个、15.0.0→875 个、25.0.0→1128 个（上限）。

经验：这类接口的报错比文档好用——服务端报什么字段名，就原样试什么字段名。

用 onnxruntime 打开就能读出全部输入输出——这是判断“能不能自己跑”的依据：

模型输入输出

us_cif_peak 是 CIF 的峰值序列，同时是“何时吐出一个字”的判据——和 Flute 里 ntp_cif/cif_calculator 是同一套思路。而 strategy.json 漏出了产品侧策略：

{ "dispatcher": { "ratio": 0.33, "max_counts": 5, "quality_score": 0.83 },
  "vad_strategy": { "max_slice_duration": 30, "min_slice_duration": 10 },
  "sentence_config": { "max_time_interval_ms": 300, "split_size": 16 } }

意思是：原始产品把长音频切成 10~30s 片，同一片可能用不同切点跑最多 5 次，再用 classifier 的质量分 （阈值 0.83）挑最好的一份——这也解释了包里为什么会带一个“质量分模型”。本项目简化成 停顿断句 + 单次解码 + 质量分只做展示（存在每句话的 quality 里，导出 JSON 能看到）。

输入 560 = 80 维 mel × 7（LFR m=7,n=6），和 FunASR Paraformer 同构；us_cif_peak 说明是 CIF / ntp_cif（和豆包输入法 Flute 里的模块同源），只是这里是明文 ONNX，onnxruntime 直接能跑。

实测（本机 CPU，纯 numpy 前端 + onnxruntime）： 「你好，这是微信语音接口测试，今天阳光很好。」 → 你好这是微信语音接口测试今天阳光很好（全对）； 「现在进行第二次接口验证，苹果香蕉橘子。」 → 现在进行第二次接口验证苹果香蕉橘子（全对）； 中英混说中文全对、英文大体对；日语是乱码（中文模型）。6 秒音频 encoder 0.49s + decoder 0.32s， 约 0.13× 实时。

./tools/fetch_offline_asr_models.sh --list     # 先看看有哪些语音模型

前端特征怎么对上（最容易翻车的一步）

PCM16 / 16k / 单声道
  → 80 维 log-mel：25ms 窗、10ms 步长、HTK mel（1127·ln(1+f/700)）、取 log
  → LFR(7,6)：连续 7 帧拼成 1 帧、步长 6 → 560 维（80 × 7 = 560）
  → 逐句归一化：(x − mean) / (std + 1e−10)          ← 逐句 CMVN
  → encoder → decoder → argmax → 8404 词表拼字（跳过 id 0/1/2，去掉 @@ 后缀）
说清楚：归一化那一步是试出来的——包里没带 CMVN 统计量，直接喂原始 log-mel 会出现 重复字（「…接口测试你好今天阳光很好」），换成逐句均值方差归一化后中文才全对。 也就是说这套前端的正确性只在这几个测试音频上验证过，换模型版本或换语种需要重新校。
边界与提醒： ① 这批模型是字节 Effect 算法分发里的公开物料，不是豆包输入法客户端自己那份 （客户端要的模型名是加密的 name_sec，扒不出它选的是哪个），只是架构同源、能力够用； ② 它属于厂商的模型资产，本项目仅用于技术研究与自用演示——别商用、别二次分发模型文件； ③ 后处理（ITN、热词、标点的细节）都有自己的模型/资源，本项目只接了标点。

2. 凭据从哪来（为什么不用登录）

豆包输入法没有任何账号体系参与语音识别，身份是「应用身份 + 设备身份」：

// 适合「把一批录音文件转成文字」：连本 Demo 的 /ws，喂 PCM，收最终文本
import fs from "node:fs";
import WebSocket from "ws";

async function transcribeFile(path) {
  const pcm = readWav16kMono(path);                       // 见 examples/asr_min.js 的 readWav
  const ws = new WebSocket("wss://<你的域名>/ws?engine=auto");
  return new Promise((resolve, reject) => {
    let done = null;
    ws.on("open", async () => {
      for (let i = 0; i < pcm.length; i += 640) {
        ws.send(pcm.subarray(i, i + 640));
        await new Promise((r) => setTimeout(r, 20));      // 按实时速度喂（也可更快）
      }
      ws.send(JSON.stringify({ type: "stop" }));
    });
    ws.on("message", (raw) => {
      const msg = JSON.parse(raw);
      if (msg.type === "final") { done = msg; resolve(msg.text); ws.close(); }
      if (msg.type === "error") reject(new Error(msg.message));
    });
    ws.on("close", () => { if (!done) reject(new Error("连接提前关闭")); });
  });
}

5. 说话人分离（可选）

上游 ASR 的结果里没有 speaker 字段，所以「谁说的」得我们自己算。 默认走 online 模式：每句一定稿就提一次声纹、和已有说话人比相似度，边录边出标签； 也可以设 DOUBAO_DIAR_MODE=batch 改成"录完整段再聚类"（更准、但要等）。

录音（16k PCM） ├─ 分割：pyannote segmentation-3.0（ONNX，6 MB）→ 逐帧说话人活动 ├─ 声纹：3D-Speaker ERes2Net（ONNX，38 MB）→ 每段的说话人向量 ├─ 聚类：余弦相似度 + 阈值（默认 0.7）→ 谁和谁是同一个人 └─ 对齐：拿每句的 [start,end] 和分离片段求最大重叠 → spk 标签

这套配方与 screenpipe 一致（它的 Rust 实现同样是 pyannote 分割 + 3D-Speaker 类声纹 + 自定义聚类）； 本项目直接用 sherpa-onnx 的现成实现，省掉自己接 ONNX。

./venv/bin/pip install -r requirements-diarization.txt   # sherpa-onnx + numpy
./tools/fetch_diarization_models.sh                       # 下模型到 ./models（走 hf-mirror）
实测结果
速度online：每句约 50ms（实时出标签）；batch：19.3s 音频约 8s（≈2.4× 实时）
中文女声 + 英文男声正确分成 2 人（阈值 0.7）
单人录音只有 1 人，不会硬拆

声纹库：从"1 号 2 号"升级到"这是谁"

分离只给出匿名编号，而且编号只在单次录音内有意义。想跨录音认人，就把说话人的声纹存下来做 1:N 识别： 有两种方式：① 打开 /voice 声纹管理页，念 3 段不同内容（每段 2~4 秒）， 页面会显示每段的质量和"与前几段的一致性"，保存即入库（推荐，最干净）； ② 在录音页点「说话人 N」标签、填真名并确认"记住这个声音"。 入库的是那个人每段录音的声纹向量（CAM++，192 维），存在浏览器 localStorage； 每次会话开始时随 config 发给服务端，新句子先跟声纹库比余弦（默认阈值 0.5）， 认得就用真名（页面显示 ✓ 姓名），认不出再走会话内聚类。一个人可存多例， 检索取"最像的那一例"。

实测：在声纹管理页录 2 段注册「小飞」→ 回录音页边说边显示 ✓ 小飞； 同一段里没注册的英文男声保持「说话人 2」——不会把陌生人硬塞成已注册的名字。
声纹模型怎么挑（实测 2 人 × 3 段）： ERes2Net-zh（38MB，中文专用）同人最低相似度 +0.29、异人最高 −0.02，可分性只有 0.31； 换成 CAM++ zh_en（28MB，中英双语）后同人 ≥ +0.72、异人 ≤ +0.05，可分性 0.67， 阈值 0.5 很安全。多例注册还有额外增益：1 秒短句 1 例 9/10 正确 → 4 例 4/4（A-B 分差 0.54 → 0.63）。
局限：不做重叠语音（两人同时说话归给其中一人）；在线追踪是逐句独立判断， 说话人编号只在这一次录音内有意义（跨录音不会自动认人，要认人得自己建声纹库）； 太短的句子（<0.6s）算不出可靠声纹，会继承上一位说话人。

6. 离线 / 本地方案

本项目自带离线引擎（offline_engine.py）：用的是字节公开分发的 ASR 模型 （见 1.7），纯 ONNX + onnxruntime，不联网、不依赖豆包客户端。 网页上可以三档切换，方便对比效果：

档位走哪条路特点
自动（默认）engine=auto：云端优先，握手失败/会话中断/重连失败 → 自动切离线引擎（再不行才用 FunASR）日常用
在线engine=cloud：只用豆包云端最准、带标点、有热词上下文
离线engine=offline：只用本机 ONNX 模型断网可用、有真实句级时间戳与质量分；英文弱一些

每次会话的分隔线上会标出用了哪档（如 2026-10-17 03:33 · 离线 · 录音 43s / 识别到 42s），方便回溯对比。

6.1 离线引擎内部是怎么做的

它是个独立进程（默认 127.0.0.1:4272），接口形状和 FunASR 引擎完全一致， 所以 server.py 里两套本地引擎复用同一个客户端基类 ChunkEngineSession—— 换引擎只是换 URL 和“结果怎么翻译成前端要的行”。

浏览器 ──20ms PCM 帧──▶ server.py ──100ms 一批──▶ offline_engine.py
                          │                        ├─ 能量 VAD 切句
                          │                        ├─ encoder → decoder → argmax（整段）
                          ◀─ 定稿句（时间戳/质量分）─┤  punc 模型补标点
                          ◀─ 未定稿片段（每约1.2s）─┘
                          └─ 转成前端的 update / final 协议

POST /stream               → {"session_id": …}
POST /stream/{sid}/chunk   → {"sentences":[{start,end,text,quality}], "partial":"…", "audio_seconds": …}
POST /stream/{sid}/finish  → 全部句子
GET  /health               → 是否就绪 / token 数 / 是否带标点 / VAD 参数

切句与“未定稿”（体验的关键，也是踩过坑的地方）

踩过的坑：把人话切碎了 → 输出全是乱码。 最初是“停顿 0.6s 就断句”，上线的真人使用反馈是 炸很炸还炸（质量分 0.001）、我的是（0.001）、这是还是一个（0.000）—— 完整句的质量分是 0.44~0.72，碎片几乎为 0。复现结论： 这个模型在 1~2 秒的碎片上会输出乱码（把测试音频硬切成 1.2s 碎片，立刻复现同样的质量分与乱码）。 于是改成“宁可晚一点合，也不要把话切碎”，并用**模型自己的质量分**当断句闸门。
参数值为什么这么定
停顿（考虑断句）1.0s短于它的停顿一定是句内停顿，绝不切
合并宽限再等 1.5s停顿够久但质量分不够 → 继续合并；到期才无条件定稿
质量闸门0.35考虑断句时先解码看一眼：质量分≥ 0.35 才真断（碎片乱码实测 0.001~0.29，完整句 0.44~0.72）
最短解码片段1.2s比这更短的片段根本不去试断句（模型必然乱码）
段内长静音压到 0.18s合并后段内还有几秒静音时，模型会重复吐字（如「接口接口测试」），压短后就干净
单段上限15s解码整段跑，太长则慢、实时性差
解码后拆行按 。！？ 拆合并出来的长段按标点拆成一行一句，时间按字数比例分
未定稿≥2.0s 才出，约 1.2s 一次太短的未定稿就是乱码，会在页面上闪垃圾字；缓冲 >8s 就不再出
底噪估计自适应3 帧滑动平均 + 静音帧 EMA；阈值 = max(0.0035, 1.8 × 底噪)
并发推理串行CPU 上并发跑只会互相拖慢，加锁排队
顺带修的一处：关掉浏览器的麦克风前处理。 getUserMedia 默认开 noiseSuppression / autoGainControl / echoCancellation， 这些对通话友好、对 ASR 有害（降噪会吞辅音、引入音乐噪声），小模型会因此重复吐字。 本项目已改成关闭（个别浏览器不支持时退回默认）。

  • 真·端侧：现在“离线”指的是推理在本机服务器、不联网；要完全不出服务端，得把 encoder/decoder 搬进浏览器 WASM（模型 160MB+，加载与内存都考验）
  • ITN：asr-itn-fst.fst 还没接（数字/单位/日期书面化）
  • 热词：离线模型输入里没有 context 字段，目前只能事后同义替换；原始产品走的是“多次解码 + 质量分挑选”
  • 流式编码器：现在是整段解码 + VAD 切句，做不到云端那种逐字上屏

离线引擎怎么跑

# 1) 下模型（约 310MB，公开 CDN；详见 1.7）
./tools/fetch_offline_asr_models.sh

# 2) 装依赖 + 起服务（默认监听 127.0.0.1:4272）
./venv/bin/pip install -r requirements-offline.txt
./venv/bin/python offline_engine.py                 # 前台
./venv/bin/python offline_engine.py --selftest tests/fixture-6s.wav   # 不进服务，直接自测

# 3) 让网页用上它（.env）
DOUBAO_OFFLINE_ENGINE=http://127.0.0.1:4272

# 4) 生产用 systemd（仓库外，部署环境里）
systemctl enable --now doubao-offline-asr

离线引擎的切句策略：能量 VAD（自适应底噪）+ 停顿 0.6s 断句 + 单段上限 12s； 一段话说到一半会每约 1.2s 给一次「未定稿」结果，前端表现为最后一行还在变，停顿后定稿并加标点。

7. 常见问题

Q：离线档认出来的字不对/在重复，怎么办？

先看句子后面有没有黄色小问号（低置信标记）——那说明这句的质量分低于 0.35。 离线模型对输入比云端敏感，常见原因：说话太快或停顿很多（会被合并/切分）、环境噪声大、麦克风增益过低。 自检顺序：① 用 ./offline_engine.py --selftest tests/fixture-6s.wav 确认引擎本身正常； ② 看 /var/log/doubao-offline-asr.log 里每句的质量分；③ 换成「在线」档对比，判断是音频问题还是模型问题。

Q：为什么我自己连不上，一直 50700000？

上游随机抖动（实测约 1/5），重试整段即可。如果重试也一直失败，可能是接口变了或被风控，换新设备试试、或改用本地引擎。

Q：直接用 whisper-1 模型名行不行？

不行，这不是 OpenAI 接口。字段 5 是固定的方法名，音频字段是裸 PCM/Opus，不解析 multipart。

Q：能不能不注册设备、硬编码一个 app_key？

不建议：app_key 按设备下发且会轮换，硬编码很快就失效；而且那属于拿别人的凭据。

Q：识别结果能拿到逐字时间吗？

能，在 results[].alternatives[].words[] 里（注意 end_time 偏大，需要按 1.3 的坑校正）。

Q：能做成 OpenAI 兼容的 /v1/audio/transcriptions 吗？

能，服务端包一层即可：接收 multipart → 转 16k PCM → 走本节协议 → 返回 {"text": ...}。 本 Demo 目前只提供了 WebSocket 接口，需要 HTTP 版可以照着 4.2 的协议自己加。

本文所有结论均来自对公开安装包的分析与实测（2026-10-16）。项目与腾讯、字节跳动、豆包均无隶属关系； 接口为未公开的内部接口，仅供技术研究，请勿用于对外商业产品。相关代码示例按 MIT 使用。
